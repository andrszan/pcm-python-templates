# 项目按需扩展指南

## 1. 本指南的目的

本指南面向当前项目维护者与 AI agent。当前项目提供一个可运行、业务无关的 FastAPI + 同步 SQLAlchemy + PostgreSQL 基线，不是完整的业务架构。

项目开始进入业务开发后，应根据真实需求增加或调整能力：

- 已有能力能满足需求时，直接复用，不重复实现；
- 只有出现真实职责时，才增加目录、依赖和架构层；
- 现有默认与项目约束冲突时，应修改现有实现并同步测试、README、`.env.example` 和 OpenAPI，而不是在旁边叠加第二套规则；
- 不用业务样例、万能基类或空目录掩盖尚未决定的需求。

本指南不是 CRUD、认证、消息队列或部署平台教程；它只说明如何判断扩展边界。

## 2. 当前基线地图

开始修改前先阅读 [README](../README.md) 与 [AGENTS](../AGENTS.md)，再阅读直接相关源码和测试：

| 位置 | 当前职责 |
|---|---|
| `src/app/main.py` | 创建 FastAPI、注册基础设施并挂载路由；不放业务实现 |
| `src/app/api.py` | 业务 router 聚合点；由 `API_PREFIX` 统一挂载 |
| `src/app/health.py` | 根级 `/health` 与 `/ready` 探针 |
| `src/app/core/config.py` | Settings、环境变量与 PostgreSQL URL |
| `src/app/core/database.py` | SQLAlchemy `Base`、engine、Session、`get_db` 与生命周期 |
| `src/app/core/responses.py` | `ApiResponse[T]`、`Page[T]`、`PageParams` |
| `src/app/core/errors.py` | HTTP/422/500 错误响应与敏感信息边界 |
| `src/app/core/middleware.py` | request ID、访问日志、CORS 与未处理异常边界 |
| `alembic/env.py` | Alembic 连接配置与唯一 `Base.metadata` 接入点 |
| `tests/test_infrastructure.py` | 当前基础设施契约和 PostgreSQL 集成测试 |

当前已提供：同步 PostgreSQL 连接、请求级 Session、Alembic、业务响应与页码分页类型、错误处理、探针、CORS allowlist、request ID、最低限度访问日志、pytest/Ruff/build 命令。

当前未提供：业务模型、认证授权、用户/权限、缓存、消息队列、任务调度、WebSocket、Docker、CI 和云平台部署。不要因为本指南提到某项能力就把它当成已安装或已接入。

## 3. 扩展前的决策流程

每次新增能力按以下顺序处理：

1. **从项目文档确认目标。** 先区分用户明确要求、可从上下文可靠推断的默认，以及真正未决的业务选择。
2. **查现有实现和所有调用方。** 复用 `core` 中已有能力，追踪被修改函数的调用路径，不在每个调用方重复打补丁。
3. **识别影响等级。** 低影响的工程默认可以直接采用；涉及公开 API、数据模型、权限/安全、数据迁移、合规或部署拓扑的实质歧义，先提出一个具体问题。
4. **选择最小方案。** 先加能证明需求的最少代码，不为未来建立 service、repository、缓存、队列或配置开关。
5. **记录变更契约。** 同步更新配置示例、README、OpenAPI、迁移说明和测试；不要让代码行为只存在于 agent 的隐含判断中。
6. **完成真实验证。** 先跑静态检查和默认测试；涉及 PostgreSQL、迁移、外部服务或部署时，再执行对应的专用验证并明确报告未验证部分。

## 4. 新增第一个业务资源/API

没有业务职责时，不要预建 `models/`、`schemas/`、`services/`、`repositories/` 等目录。第一个真实资源出现后，再按项目需要创建相应文件。

推荐的最小顺序：

1. 确认资源的公开路径、请求/响应字段、状态码、错误语义和是否需要认证；
2. 创建该资源的 Pydantic 请求与响应 schema；
3. 创建继承 `app.core.database.Base` 的 SQLAlchemy 模型；
4. 在资源 router 中实现端点；
5. 将 router 注册到 `app/api.py`，不要在资源文件硬编码 `/api/v1`；
6. 成功响应显式使用 `ApiResponse[T]`，列表响应复用 `Page[T]` 与 `PageParams`；
7. 增加成功路径和明确失败分支的最小测试；
8. 验证 `{API_PREFIX}/openapi.json` 与 `{API_PREFIX}/docs`。

`main.py` 继续只做装配。只有跨业务且确实稳定的横切能力才进入 `core/`；单个资源的业务规则不要放入 `core`。

## 5. 数据模型、Session 与 Alembic

### 模型

新增模型使用现有 `Base`。主键类型、时间戳、审计人、软删除、多租户、金额精度、时区、枚举存储、索引、外键和级联都属于项目数据语义，不能仅凭“常见做法”决定。

### 迁移

每次 schema 变化都必须：

1. 确保模型被 Alembic 的 metadata 导入；
2. 生成 migration revision；
3. 人工审查 nullable、默认值、索引、约束、外键、数据回填和锁表影响；
4. 根据部署策略决定迁移与应用版本的先后关系；
5. 使用专用、可丢弃的 PostgreSQL 验证 upgrade，必要时验证 downgrade 或回滚方案。

禁止：

- `Base.metadata.create_all()` 代替迁移；
- 在应用启动或 lifespan 中自动执行 migration；
- 在测试 fixture 或业务路由中偷偷建表；
- 把未经审查的 `--autogenerate` 输出直接交付。

### Session 与事务

`get_db` 只负责请求级 Session 的创建和关闭，不自动提交。简单端点可以直接使用 Session，不要为了“分层完整”先创建 service/repository。

业务代码应围绕一个明确的业务操作决定事务边界：成功时显式 `commit()`；预期数据库异常后，在继续使用 Session 前显式 `rollback()`。只有跨多个端点复用稳定业务规则时再提取 service/use-case，只有数据访问逻辑确实复用或需要替换时再考虑 repository。

## 6. API 契约、分页与探针

- 业务路径统一由 `API_PREFIX` 控制；不要在各业务 router 中硬编码版本前缀。
- 端点使用 `APIRouter`、tags、summary、Pydantic schema 和明确的 `response_model`。
- 业务成功响应使用 `ApiResponse[T]`；错误信息只返回经过审查的公开内容，不能把原始输入、SQL、异常对象或第三方错误直接放入 `HTTPException.detail`。
- 分页使用 `PageParams` 的 page/size；查询必须有稳定、显式的排序。具体排序字段由业务语义决定；`total` 表示同一筛选条件下的总数；页码越界默认返回空列表，除非项目契约另有规定。
- 不预建 cursor、查询 DSL、通用 CRUD 或全局自动响应包装器。
- `/health` 永远只表示进程存活，不访问数据库；`/ready` 当前只做 `SELECT 1`。新增外部依赖探针前，先定义其 liveness/readiness 语义和失败是否应阻断流量。
- 文件上传/下载、流式响应、Webhook、幂等键、限流、WebSocket 等改变 HTTP 契约的能力，只在真实需求明确后单独设计。

## 7. 认证、授权与多租户

这些能力不能用“通用 JWT 示例”代替项目设计。开始实现前确认：

- Session、Cookie、Bearer token 还是外部身份提供方；
- token 的签发、过期、轮换、吊销、存储和传输方式；
- 401/403 的公开语义；
- 角色权限、资源级授权还是其他策略；
- 租户来源、数据隔离、查询约束和后台任务边界。

认证和授权出现后，更新 Settings、OpenAPI security scheme、测试与日志脱敏规则。密码、token、Cookie、Authorization 和用户输入不得进入日志。不要在没有身份模型和安全契约时加入登录路由、RBAC、refresh token 或 token blacklist。

## 8. 配置、秘密与新依赖

- 新的运行配置统一加入 `app/core/config.py`，同步 `.env.example`、README 和测试；不要在业务模块读取 `os.environ`。
- 密钥只能来自运行环境或秘密管理服务，不能写入源码、迁移、测试输出或文档中的真实值。
- CORS 继续使用明确 allowlist；不要为了开发方便把生产配置改成任意 origin + credentials。
- 新依赖必须有真实消费者、明确版本范围、锁文件更新、许可证/安全影响评估和最小测试；已安装不等于已接入。
- 只有跨业务、稳定且无法由现有模块承担的横切能力才进入 `core/`；业务专属工具留在业务模块附近。

## 9. 缓存、任务、队列与外部服务

按需求强度选择，不要预装基础设施：

- 可随请求结束丢失、无重试要求的短工作，才考虑进程内 background task；
- 需要重试、持久化、调度、削峰或跨实例执行时，再引入外部任务/消息系统；
- 缓存先定义 key、TTL、失效、一致性容忍度和击穿/穿透策略，再决定是否引入 Redis 等依赖；
- 外部服务接入必须定义超时、重试、幂等、失败响应、日志和 readiness 影响；
- 多副本部署后不得依赖进程内共享状态。

## 10. 日志、指标与部署

在现有 request ID、访问日志和探针上增量演进：

- 先确认日志采集平台和字段要求，再决定是否需要结构化日志、指标、trace 或错误上报；
- 继续禁止记录 body、query string、Authorization、Cookie、token、密码、数据库 URL 和敏感异常；
- readiness 表示依赖当前可用，不负责迁移或业务查询；
- Docker、Kubernetes、CI、worker 数、反向代理、TLS、proxy headers、超时和 autoscaling 都要根据实际部署目标选择；
- migration 是独立发布步骤，应用启动不自动迁移；
- 同步 SQLAlchemy 不是待自动改造的问题，只有性能测量和外部 I/O 模型证明必要时再评估异步化。

## 11. AI agent 协作清单

AI agent 开始业务开发前：

- 阅读 README、AGENTS、本指南、`main.py`、`api.py`、`health.py`、相关 `core`、`alembic/env.py` 和测试；
- 追踪现有函数的调用方和生命周期，不重复创建已有能力；
- 将事实、项目已决定事项、当前默认和待确认问题分开记录；
- 对低影响工程选择采用当前默认，不因细节不完整反复追问；
- 对 API、数据、权限/安全、迁移或部署的实质歧义提出定向问题；
- 用最少文件实现需求，不预建无职责层；
- 行为变化增加最小 pytest，并更新 OpenAPI/README/`.env.example`/migration；
- 报告哪些测试实际执行、哪些 PostgreSQL/外部依赖验证被跳过。

## 12. 反模式与停止条件

发现以下情况应停止扩展并重新确认，而不是继续堆代码：

- 为未来需求预建大量空目录或抽象；
- 没有业务模型就编写通用 CRUD、repository、UoW 或查询 DSL；
- 用 `create_all()` 或启动自动 migration 掩盖部署流程未定义；
- 未经测量把当前同步 PostgreSQL 技术栈改成异步、多数据库或另一套 ORM；
- 将异常、请求体、token、数据库 URL 或第三方原始响应写入日志/错误响应；
- 以默认 JWT、宽泛 CORS 或硬编码密钥换取“快速可用”；
- 只修改代码不修改测试、OpenAPI、配置示例和文档；
- 把“已安装依赖”或“文档提到的能力”误报为“已接入能力”。

## 13. 扩展后的交付检查

在项目目录执行并记录结果：

```bash
uv sync --locked
uv run --locked ruff check . && uv run --locked ruff format --check .
uv run --locked pytest
uv build
```

根据本次需求追加：

- 专用 PostgreSQL 的集成测试；
- `alembic upgrade head` 与必要的迁移回滚验证；
- OpenAPI JSON、Swagger UI 和关键状态码检查；
- 认证、外部服务、任务、缓存或部署平台的专用验证。

检查当前项目能独立安装、运行、测试和构建；确认 `.env`、真实密钥、个人路径、缓存与生成产物没有进入交付。若 PostgreSQL integration 未运行，明确写“数据库行为未验证”，不要写成通过。
